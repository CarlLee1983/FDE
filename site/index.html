先修作業，再選技術。

FDE 走進一個具體工作現場，把模糊需求整理成可決策的作業方案：界定問題、診斷流程、重分責任、選擇最簡充分介入，最後交出下一個 accountable action。

AI 可以是答案，也可以不是。

案例證明推理與交付形狀，不證明任何企業已接受、授權、上線或取得成效。

穩定規則交給軟體，語言負擔才考慮 AI。權限、政策與持久影響仍由可歸責的人與受治理系統承擔。

一條從問題走到下一步的工作線

不是固定文件清單，也不是預設開發 roadmap。每一步只增加足以支撐下一個可靠決策的深度。

  1. 1.0

    Frame
    界定

    確認使用者、工作節點、真正結果與本次要做的決策。沒有企業證據時，把推論標成可驗證假說。

    完成：問題有邊界，下一個決策清楚。
  2. 2.0

    Diagnose
    診斷

    追蹤正常、例外、升級與 rework。找出等待、重複檢查、語義歧義與沒有降低風險的控制。

    完成：真正的作業原因可被說明。
  3. 3.0

    Redesign
    重整

    先移除、簡化、標準化與重新分責；再比較流程改變、資訊修復、確定性軟體、人類判斷與 AI。

    完成：技術選擇建立在較好的工作流上。
  4. 4.0

    Decide
    形成方案

    交付證據有界的 operating solution，說明 AI-fit、限制、驗證方式與下一個 accountable action。

    完成：使用者能選擇實作、驗證、延後或停止。

FDE skill 的責任是讓方案可被可靠地決定與交接。只有使用者另外要求開發，目標 repository 的開發 agent 才依當地架構、依賴與測試規範實作。

  1. Operating solution
    問題、流程、責任、介入與證據界線。
  2. Development handoff
    第一切片、輸入、模組 seam、驗收與禁止事項。
  3. Repository delivery
    開發 agent 讀取當地規範，實作、測試並回報剩餘風險。

我們只聲稱證據允許的事

Repository 裡的 schema、fixtures、replay 與 HTML 可以證明案例結構和本地行為；它們不能代替企業 owner、真實資料授權、production control 或成效量測。

  • Evidenced有可追溯來源與足夠新鮮度的 repository 或企業證據。
  • Proposed可供 owner 評估的設計、流程或驗收條件。
  • Missing必須由 accountable owner 或目標系統補齊的輸入與授權。
  • Unverifiable目前無法從可用證據確認，因此限制主張或下一步。
