# Collaborative clarification

Use this workflow when a requested FDE analysis lacks a bounded outcome, decision or action, process location, accountable owner, or other prerequisite whose answer materially changes the solution. Read `Collaborative Clarification` in the canonical scenario-to-action method first.

## Clarification loop

1. **Build the decision tree.** Turn material unknowns into decisions and connect each decision to its prerequisites. Include only branches that can change the operating diagnosis, target workflow, intervention, authority, validation, or next action.
2. **Resolve facts.** Inspect supplied evidence, repository sources, and available systems for facts the agent can establish. Record provenance and freshness; mark unavailable facts `missing` or `unverifiable`. Do not ask the user to retrieve evidence the agent can inspect safely.
3. **Ask the frontier.** Ask together only decisions whose prerequisites are settled. Give each question a recommended answer, its evidence basis, and the consequence of choosing differently. The accountable participant decides intent, policy, ownership, trade-offs, and acceptance.
4. **Recompute.** Record each answer and rationale, expose the next newly unblocked decisions, and repeat. If an answer changes an earlier assumption, revise the affected branch before continuing.
5. **Synthesize into FDE work.** Write settled answers, supporting evidence, and unresolved branches into the scenario record, operating-solution proposal, evidence ledger, or gate review used by the selected task mode. Do not create a separate interview transcript as the authoritative result.

## Clarification completion

Every material branch is decided, evidenced, `missing`, or `unverifiable`; no downstream decision rests on an unsettled prerequisite. The selected FDE output identifies the bounded outcome, user, process or case location, decision or action, evidence boundary, and next accountable owner. This completion establishes shared understanding only; the applicable FDE gate still determines approval and authority.

## Revising on new information

Use this section when information arrives after a conclusion exists and may change the bounded problem, target workflow, intervention, authority, acceptance, or value judgement. Reconcile before rewriting.

1. **Preserve the prior conclusion.** Keep the earlier claim, its assumptions, and its evidence basis readable. Do not silently overwrite an answer that was sound on its inputs.
2. **Bound the new information.** State its source, when it was observed, which version of a policy, system, or definition it describes, and the scope it applies to — market, product line, amount band, role, system, or time window.
3. **Classify the relation** to each affected conclusion as `supplements`, `conflicts`, `supersedes`, or `coexists` under a different scope. Use `supersedes` only when an authoritative statement replaces the earlier one within the same scope.
4. **Separate recompute from retain.** Name the conclusions that must be reworked and the conclusions that still hold, and say why each retained conclusion survives the new information.
5. **State the revised recommendation and what stays open**, using the existing evidence states.
6. **Name the work that can continue** while an open decision is pending, and the work that must wait for it.
7. **Update an ongoing case in place.** Change only the affected parts of the scenario record, proposal, or evidence ledger, and keep the reason for each change with it.

Hold these limits while reconciling:

- Newer is not automatically more authoritative.
- A system being able to do something is not a policy authorization to do it.
- A requester is not automatically an approver or an acceptor.
- A walkthrough, one team, one site, or one period is a local observation, not a population fact.
- An inference or a pending assumption stays labelled as one and never becomes a confirmed fact.
- Use `evidenced`, `proposed`, `missing`, and `unverifiable`; do not introduce a competing classification.

## Unknowns that drive verification

For each unknown that changes the next decision, state the question, which decision each possible answer changes, how it can be verified, which role can supply the evidence or make the decision, what result closes it, and which part of the analysis is recomputed when the result returns. Order unknowns by decision impact, then dependency, then verification cost.

Investigate the facts obtainable from supplied material, repository sources, and safely inspectable systems yourself; ask people only for policy, scope, ownership, and trade-off decisions. When the accountable role is unknown, mark it `missing` rather than naming a person or implying an authorization. A single analysis states this inline; an ongoing case updates the existing record instead of starting a parallel one.
