# Collaborative clarification

Use this workflow when a requested FDE analysis lacks a bounded outcome, decision or action, process location, accountable owner, or other prerequisite whose answer materially changes the solution. Read `Collaborative Clarification` in the canonical scenario-to-action method first.

## Clarification loop

1. **Build the decision tree.** Turn material unknowns into decisions and connect each decision to its prerequisites. Include only branches that can change the operating diagnosis, target workflow, intervention, authority, validation, or next action.
2. **Resolve facts.** Inspect supplied evidence, repository sources, and available systems for facts the agent can establish. Record provenance and freshness. When a fact is out of the agent's reach, request it from a role that holds it and mark it `missing` or `unverifiable` until it returns. Follow `Facts and decisions` below.
3. **Ask the frontier.** Ask together the decisions whose prerequisites are settled and the fact requests from step 2, keeping the two kinds visibly apart. Give each decision a recommended answer, its evidence basis, and the consequence of choosing differently. The accountable participant decides intent, policy, ownership, trade-offs, and acceptance.
4. **Recompute.** Record each answer and rationale, expose the next newly unblocked decisions, and repeat. If an answer changes an earlier assumption, revise the affected branch before continuing.
5. **Synthesize into FDE work.** Write settled answers, supporting evidence, and unresolved branches into the scenario record, operating-solution proposal, evidence ledger, or gate review used by the selected task mode. Do not create a separate interview transcript as the authoritative result.

## Clarification completion

Every material branch is decided, evidenced, `missing`, or `unverifiable`; no downstream decision rests on an unsettled prerequisite. The selected FDE output identifies the bounded outcome, user, process or case location, decision or action, evidence boundary, and next accountable owner. This completion establishes shared understanding only; the applicable FDE gate still determines approval and authority.

## Facts and decisions

Who knows a fact and who may decide it are different questions. Answer them separately.

- **Investigate what you can reach.** When the fact is in supplied material, a repository source, or a system the agent can inspect safely, read it. A policy document already provided is read, never handed back as a question.
- **Ask a knowing role for what you cannot reach.** Missing data, missing access, or a fact that only on-site experience can confirm is a request for evidence, not a decision. Name the artefact or observation you need and the role that holds it, and do not claim the agent can verify it alone.
- **Route decisions to authority.** Policy change, scope trade-offs, and authorization belong to the accountable role, not to whoever described the behaviour.
- **Assume no permission and no approval right.** The agent has only the access it has been given; the user approves only what they have been stated to own.
- **Keep an unconfirmed account as an account.** An unverified spoken statement keeps its named source and the scope it can support. A system being able to do something is a system behaviour, not a policy authorization.

## Revising on new information

Use this section when information arrives after a conclusion exists and may change the bounded problem, target workflow, intervention, authority, acceptance, or value judgement. Reconcile before rewriting.

1. **Restate the case scope.** Name the bounded problem the case is answering, its open decisions, and the facts, rules, and assumptions the existing conclusions rest on. Reconcile against that scope, not against the wider topic the new information belongs to.
2. **Preserve the prior conclusion.** Keep the earlier claim, its assumptions, and its evidence basis readable. Do not silently overwrite an answer that was sound on its inputs.
3. **Bound the new information.** State its source, when it was observed, which version of a policy, system, or definition it describes, and the scope it applies to — market, product line, amount band, role, system, or time window.
4. **Classify the relation** to each affected conclusion as `supplements`, `conflicts`, `supersedes`, or `coexists` under a different scope. Use `supersedes` only when an authoritative statement replaces the earlier one within the same scope.
5. **Test for dependency before recomputing.** A conclusion is recomputed only when the new information changes a fact, rule, or assumption that conclusion depends on. Information under a different scope with no such dependency leaves the conclusion, its target workflow, and its controls exactly as they are, and produces no recompute task and no new open decision. When a cross-scope dependency does exist, name the dependency and what it changes before proposing any revision.
6. **Separate recompute from retain.** Name the conclusions that must be reworked and the conclusions that still hold, and say why each retained conclusion survives the new information.
7. **State the revised recommendation and what stays open**, using the existing evidence states.
8. **Name the work that can continue** while an open decision is pending, and the work that must wait for it.
9. **Update an ongoing case in place.** Change only the affected parts of the scenario record, proposal, or evidence ledger, and keep the reason for each change with it. When the new evidence's replacement scope is unclear, leave the affected part open and say why, rather than overwriting it.

Hold these limits while reconciling:

- Newer is not automatically more authoritative.
- A system being able to do something is not a policy authorization to do it.
- A requester is not automatically an approver or an acceptor.
- A walkthrough, one team, one site, or one period is a local observation, not a population fact.
- An inference or a pending assumption stays labelled as one and never becomes a confirmed fact.
- Use `evidenced`, `proposed`, `missing`, and `unverifiable`; do not introduce a competing classification.
- A different scope with no dependency on a conclusion is context, not a reason to revise it.
- Widening the analysis — a cross-scope comparison, a simplified control, an approval matrix, a broader process — is an optional suggestion carrying its reason and its cost. It never becomes a work requirement, an open decision the user must close, or a change to the agreed target workflow.
- An unstated scope is asked about, not assumed. One market's case is not a request to design a global rule.

## Unknowns that drive verification

For each unknown that changes the next decision, state the question, which decision each possible answer changes, how it can be verified, which role can supply the evidence or make the decision, what result closes it, and which part of the analysis is recomputed when the result returns. Order unknowns by decision impact, then dependency, then verification cost.

Split every unknown the way `Facts and decisions` requires: investigate what is reachable, request from a knowing role what is not, and route decisions to the accountable role. When the accountable role is unknown, mark it `missing` rather than naming a person or implying an authorization. A single analysis states this inline; an ongoing case updates the existing record instead of starting a parallel one.
