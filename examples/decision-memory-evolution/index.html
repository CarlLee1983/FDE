真正缺少的不是另一張報表

一般報表回答「現在發生什麼」。決策記憶還要保存「當時知道什麼、如何判斷、做了什麼，以及後來結果如何」。

一句話版本：把每一次商業判斷變成可追溯的決策鏈；AI 從重複修正中提出改善候選，但不能把單次經驗直接升格為正式政策。

為什麼同一種問題總要重新調查？

舊流程
  1. 週報發現客戶訂購下降。
  2. 分析人員分別查訂單、客服和續約。
  3. 會議形成判斷，請業務跟進。
  4. 理由留在簡報、訊息或人的記憶裡。
  5. 相似案例出現時，再從頭調查。
應先修復
  • 統一重大變化與比較期定義。
  • 把事實、假設和決策分開保存。
  • 限制第一版決策為 monitor／verify／escalate。
  • 決策當下指定觀察期限與結果。
  • 讓後續結果回連原始訊號。

客戶 A：訂購下降不等於已經流失

這些合成數字只用來呈現證據形狀。它們可以觸發審閱，不能直接建立因果或客戶標籤。

一筆完整的決策記憶長什麼樣？

DecisionEpisode 不可被覆寫；修正只能追加新版本。歷史重播也只能看到決策當時已存在的資料，不能偷看後來結果。

訊號四週訂購金額下降 24%；合成來源 orders-snapshot:r17，as-of 2026-07-31，語意版本 0.1.0，新鮮度 fresh，access decision demo-read-17。
解讀主管認為需確認採購排程與服務影響；明確標示為假設。
決策選擇 verify，由帳戶負責人在五個工作日內查證。
觀察三十天後訂購恢復；這是結果，不單獨證明原假設正確。
能力候選八筆合成案例都漏看 as-of 未結服務事件，提議建立 assembleAccountReviewContext()；經重播與 owner 接受後才成為確定性工具。

兩條迴路，讓記憶變成能力

營運迴路

把今天的判斷留下來

  1. 取得可信訊號與證據。
  2. 人類區分事實和假設。
  3. 記錄決策、理由和 owner。
  4. 到期後補記結果。
  5. 形成完整決策時間線。
↔
演進迴路

把重複經驗變成新能力

  1. 比較修正、例外與結果。
  2. 找出重複調查模式。
  3. 提出具名能力候選。
  4. 以封存案例重播比較。
  5. owner 接受後才開發發布。

第一個切片：先建立沒有 AI 也有用的決策時間線

包含
  • 一個商業單位、10–20 筆可用案例
  • 一套已接受的變化 baseline
  • 來源、新鮮度、語意版本與 access decision
  • 受控、append-only 的決策 journal action
  • 到期結果與原訊號回連
延後
  • AI 正式進入營運迴路
  • 自動判定客戶流失
  • 客戶聯繫、派工或 CRM 寫入
  • 一次涵蓋全公司資料
  • AI 自行發布新規則或工具
來源讀取是唯讀，但 journal 本身是持久寫入，仍需授權、稽核、冪等與復原證據。目前 process readiness 未通過，AI selection 是 deferred。

如何證明不是漂亮的故事？

1. 重播用封存案例量測現有人工調查時間與決策鏈缺漏。
2. 非 AI shadow在相同案例建立可信訊號與人工決策時間線。
3. AI shadowreadiness 後比較 groundedness、棄答、修正、時間、成本與安全。
4. 單一候選只選一種反覆且可規格化的修正進行重播。
5. 受治理發布owner 接受、測試與回復齊備後，營運迴路才使用新版本。

決策記憶不是自動決策權

AI 不得自行

  • 把訂購下降標記為客戶流失。
  • 把相關性寫成因果關係。
  • 聯繫客戶、指派工作或修改 CRM。
  • 根據單次結果改寫政策。
  • 接受並發布自己提出的能力。
  • 擴大資料權限或隱藏缺少的證據。

正確順序是：AI 提議 → 封存案例重播 → 負責人接受 → 開發測試 → 版本發布 → 監控與回復。

下一個負責行動

由真實商業營運流程負責人召集主管、帳戶負責人、分析人員與資料 owner，確認現況流程，並選定一個商業單位與 10–20 筆可合法使用的案例。

完成條件：目標流程獲得 owner 與使用者接受；來源、定義和權限有直接證據；交付團隊能從訊號重播到人工決策和到期結果。
