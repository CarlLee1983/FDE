00

Process-first operating solution · 先講結論

先交付不含 AI 的「出貨延誤審閱工作台」

現行流程卡在哪裡？應先改掉什麼？第一個切片要交付什麼？

現行流程診斷

物流人員目前從每日匯出檔逐筆找案件、在腦中比較急迫訊號，再決定審閱順序。 快照是否過期、欄位是否齊全、為何排在前面，都沒有成為明確的流程入口與可追查結果。 這項診斷來自合成需求，仍需真實 process owner 與使用者確認，不能當成現場觀察結論。

先優化流程，不先選技術

1. 統一入口條件

先固定 snapshot identity、freshness SLA、必要欄位、語意版本與 access decision。

2. 把例外分出去

stale batch 整批停止；缺欄位案件進 data-quality escalation，不混入正常排序。

3. 明文化優先規則

使用同一組 score、tie-break 與 reason trace，消除每位人員重複心算與無法追查的差異。

4. 保留清楚的人員責任

工作台只提供審閱順序與證據；物流人員決定後續，第一階段不寫 ERP。

不假設 AI 的目標流程

  1. 載入唯讀快照
  2. 檢查證據與權限
  3. 規則排序或資料升級
  4. 查看證據與 reason trace
  5. 人員決定後續

Demo 的 review state 只保留在當次 session。Shadow 若要持久保存狀態與 reason code，必須先取得 identity、privacy、retention 與 telemetry access decision；規則或流程變更由具名 owner 審查。

介入方式怎麼選

流程需要 選擇 理由
判斷資料是否可進入審閱 資料契約＋確定性檢查 條件穩定、可測，不需要模型推論
減少人工反覆比較 確定性 decision service 政策已明確，相同輸入應得到相同結果
讓人員理解與質疑排序 結構化 UI＋reason trace 先用最低複雜度介面建立可比較基線
實際後續處置 人工決定；ERP write-back 延後 目前沒有 G5 授權與控制證據

第一個可交付垂直切片：不含 AI

交付一個唯讀工作台：先顯示資料能否使用，再呈現 ranked queue、escalated records、 每筆來源欄位與 reason trace，最後讓使用者標記 accepted、rejected 或 needs-investigation。

工作包 要交付的可觀察結果 完成證據
1. 驗證流程 owner 與使用者確認或修正 as-is、target、handoff 與 exception 具名 process acceptance；真實企業目前 missing
2. 凍結契約 定義 input、context、decision、escalation 與 review-state schema 契約範例可驗證；禁止 side effect
3. 規則重播 四筆資料穩定得到 90、65、35 與一筆 escalation 現有 7 個 decision tests 自動通過
4. 審閱工作台 使用者查看 queue、evidence、trace 與三種 session-local review state 正常、stale、缺欄位、質疑與調查流程測試
5. Process shadow 確認真實 identity、source、privacy、telemetry、support、baseline 與 rollback target evidence missing

AI-fit 結論：現在延後

這個流程用結構化 UI 就能直接呈現 rule trace，因此沒有理由把 AI 當成第一切片的必要條件。 只有 process shadow 證明人員在改版後仍花費顯著時間解讀或比較，而且 owner 接受 baseline、 permitted context、privacy、eval、abstention、latency／cost 與 rollback，才啟動可拔除的 explanation 實驗。 實驗必須對非 AI 工作台證明增量價值；失敗時只關閉 explanation，核心流程不受影響。

01

Frame · 先把問題縮小

界定情境：不是「做一個 Agent」，而是排出人工審閱順序

要解決的問題、使用者、輸出與禁止事項到底是什麼？

收到的需求

物流協調員每天開啟一份出貨匯出檔，逐筆找出該先處理的延誤案件。 要求 FDE 根據快照產生可解釋的優先序，讓人員決定後續動作。

我們實際做了什麼

把輸出寫清楚

輸出是「供物流人員審閱的排序建議」，不是自動派工或系統操作。

把介入位置寫清楚

發生在每日匯出檔取得後、物流人員開始人工排序之前。

把衡量方式寫清楚

合成基線是每批 45 分鐘，目標是 15 分鐘；這只是待驗證目標。

先畫出紅線

不得修改 shipment、不得寫回 ERP、不得自動派發任何工作。

02

Map Work · 先診斷，再重設流程

從人工掃描，改成正常、例外與升級各有去處

現況浪費在哪裡？先移除什麼工作？剩下哪個節點才需要系統介入？

先分清楚現況假設與目標流程

As-is：仍待現場確認

人員逐筆掃描匯出檔、心算並比較急迫訊號，同時自行發現 stale 或 missing data。

To-be：先分流再審閱

入口先驗證批次與資料；只有有效案件進排序，問題資料走明確的停止或升級路徑。

目標主流程

  1. 取得唯讀快照
  2. 檢查 freshness、權限與欄位
  3. 計算審閱優先序
  4. 交物流人員判斷
  5. 人工處理在 FDE 範圍外

真正重要的是三條路徑

路徑 觸發條件 系統輸出 為什麼這樣設計
Normal 快照新鮮，必要欄位完整 產生排序 recommendation 讓人員直接審閱，不替人員執行動作
Exception 快照超過 freshness SLA 不計分，要求重新取得快照 避免用過期證據做出看似精確的結果
Escalation 單筆記錄缺少必要欄位 該筆不計分，轉資料品質處理 缺資料時不猜測、不偷偷補預設值

介入點與權限邊界

先完成上述流程重設，才把 FDE 介入點放在「匯出檔已取得」與「人員開始人工排序」之間。 它只讀取快照並提出建議；最後的人工作業與 ERP 更新不屬於這個能力。

產出與驗證

process-model.md process-validation.json

合成的物流角色與流程角色接受了 current-process assumptions、target changes，以及 normal、exception、escalation 三條路徑； 這不是企業使用者驗收。

04

Specify Decision · 把推薦邏輯寫成可測規則

寫出決策規則：分數、邊界、同分排序與缺漏處理

為什麼某一筆是 90 分？在 24／48 小時邊界會不會算錯？

決策服務

我們建立 rank-delayed-shipment-for-review@1.0.0。 它有具名 policy owner、五個必要輸入、固定輸出與 escalation 行為。

實際規則

基本分數：只取一個延誤區間

  • overdueHours ≥ 48：50 分
  • 24 ≤ overdueHours < 48：30 分
  • overdueHours < 24：10 分

附加分數：條件成立就累加

  • serviceLevel = critical：＋25
  • temperatureControlled = true：＋20
  • atRiskCustomerCommitment = true：＋15

缺漏與同分規則

必要輸入缺漏

整筆轉 escalation，輸出原因但不產生 priority score。

分數相同

先依 overdueHours 由高到低，再依 shipmentId 由小到大。

我們跑了 7 個測試

測試類型 涵蓋內容 結果
正常結果 × 3 SHP-1001／1002／1003 分別得到 90／65／35 passed
缺漏升級 × 1 SHP-1004 缺 overdueHours，不計分 passed
邊界 × 2 剛好 24 小時得 30 分；剛好 48 小時得 50 分 passed
同分排序 × 1 驗證 overdueHours 與 shipmentId 的排序順序 passed
