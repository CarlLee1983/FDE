# 新資訊調解：訪談指出系統可跳過退款批准

先講結論：這則訪談**不推翻**「台灣案件退款需人工批准」這個結論，它談的是另一件事——系統有沒有把這條規則**擋住**。原結論是政策層的規則陳述，訪談是單一第一線人員對系統行為與現場做法的口述。兩者不是同一層，因此關係是 `supplements`（補充），不是 `supersedes`。真正被這則資訊改變的，是「這條規則目前靠什麼保證」這個假設，以及隨之而來的控制設計。

## 1. 保留既有結論與其基礎

原結論：**台灣案件退款需人工批准。**
- 性質：政策／規則層的要求陳述。
- 這條結論在原有輸入下仍然成立，不因為有人做得到繞過就失效——「做得到」不等於「被允許」。
- 但它底下有一個先前未明說的**隱含假設**：批准要求是有效落實的（系統強制或流程可稽核）。這個假設現在被質疑了。

## 2. 界定新資訊的邊界

| 面向 | 內容 | 證據狀態 |
| --- | --- | --- |
| 來源 | 退款作業第一線操作人員（單一受訪者），訪談口述 | `proposed`（未經證實的陳述） |
| 觀察時間 | 未載明訪談日期 | `missing` |
| 系統版本 | 未載明所指系統與版本 | `missing` |
| 適用範圍 | 未載明是台灣全部退款、特定金額級距、特定案件類型，或特定角色權限 | `missing` |
| 發生頻率／量體 | 「趕件的時候」——條件與頻率皆未量化 | `missing` |
| 兩項不同主張 | (a) 系統技術上可跳過批准；(b) 實務上有人直接放行 | 皆 `proposed`，需分別驗證 |

界線提醒：**系統做得到 ≠ 政策授權**；一位第一線人員的說法是**局部觀察**，不是全體行為的事實；受訪者描述行為，不代表他有權決定或改變政策。

## 3. 對各項結論的影響：重算 vs 保留

**保留不變（不依賴新資訊所改變的事實）**
- 「台灣案件退款需人工批准」這條政策要求本身——訪談沒有提出任何有權來源說它被取消或放寬。
- 目標流程中「批准」這個步驟的存在與位置。
- 依附於「是否需要批准」的下游設計（誰批、批什麼、批准的判斷內容）。

**需要重算（其依賴的假設確實被動到）**
- **控制有效性判斷**：原本可假設批准是被落實的；現在必須改成「規則存在，但強制機制未經證實」。這是一個**控制缺口（control gap）**假說，而不是政策變更。
- **例外／趕件路徑的診斷**：原診斷若未涵蓋「趕件時的實際走法」，現在必須把這條非正式路徑納入現況流程圖，並釐清它是異常路徑、預設路徑，還是被默許的權宜。
- **稽核與證據能力**：跳過批准的案件是否留下可追溯紀錄，直接影響任何依賴「退款有批准軌跡」的後續主張與價值論述。

## 4. 修正後的表述

「台灣案件退款**依規定**需人工批准；該要求目前是否由系統強制、是否可被繞過、繞過是否留痕，均為 `missing`，僅有單一第一線人員的未證實陳述指出可繞過且實務上曾發生。」

原本可能寫成「已受控」的地方，降級為「規則已定義，落實情形待驗證」。

## 5. 待驗證的未知（依決策影響排序）

**(A) 系統是否真的允許跳過批准？** ——事實問題，可查證，不是決策。
- 我能自己做的：檢視已提供的權限設定、流程設定檔、系統文件（若在可及範圍內）。
- 我不能自己做的：實際系統的權限矩陣、退款流程設定、UI 實測。**向誰要**：該退款系統的系統管理員或應用負責人。
- **收斂條件**：拿到權限／流程設定的截圖或匯出，明確顯示批准節點是否可略過、在哪些條件下可略過。
- **回來後重算**：控制有效性判斷、目標流程的強制點設計。

**(B) 實際發生的頻率、金額分布與觸發條件為何？** ——事實問題。
- **向誰要**：能匯出退款交易紀錄的資料／營運分析角色。
- **收斂條件**：一段期間內退款案件中，無批准紀錄者的件數、金額與情境分布。
- **回來後重算**：這是邊緣例外還是常態繞道，決定介入強度（軟性提醒 vs 硬性阻擋）。

**(C) 跳過批准的案件是否留下可稽核紀錄？** ——事實問題。
- **向誰要**：系統管理員／稽核日誌保管者。
- **收斂條件**：日誌樣本顯示是否記錄「未經批准即放行」及操作者身分。
- **回來後重算**：稽核主張、風險評估、是否需要補建紀錄能力。

**(D) 「趕件時直接放行」是被默許的例外，還是違規？** ——**這是決策，不是事實**。
- **路由給**：退款政策的當責主管／風險或法遵負責人。受訪的第一線人員描述了行為，但無權認定其合規性。
- **選項與後果**：
  - 認定為違規 → 需要強制阻擋＋既有案件的補救與通報。
  - 認定為正當例外 → 政策必須明文化例外條件、授權層級與留痕要求，否則等於無控制。
  - 維持現狀不表態 → 規則形同虛設，任何依賴批准軌跡的主張都不成立。
- 當責角色若尚未確認，標記為 `missing`，不擅自指定人選。

## 6. 介入方向（待 A–D 收斂後定案，此處僅為方向）

依「穩定規則交給軟體，語言負擔才考慮 AI」：**批准與否是穩定規則與權限問題，屬於確定性軟體與流程控制的範疇，AI 不適用（`AI not needed`）**。真正的候選介入是——先問「趕件時為什麼需要繞過」（若批准本身是不必要的等待，正解可能是**簡化或重新分派批准**，而不是加強阻擋），再決定是在系統中強制批准節點、為趕件情境設計有授權、有留痕的快速通道，或兩者並行。在 (A)(B)(D) 回來之前，選哪一個都缺乏依據。

## 7. 可以並行、與必須等待的工作

**可以繼續**：現況流程圖補上「趕件路徑」這條分支；整理批准步驟目前實際承擔什麼風險（它到底在防什麼）；準備 (A)(B)(C) 的證據請求清單。

**必須等待**：控制設計定案、任何「退款已受控」的價值或合規主張、以及是否要在系統中加上硬性阻擋——後者取決於 (D) 這個政策決定。

## 8. 一項可選、非任務的建議

若貴方想知道同樣的控制缺口是否存在於其他市場或其他需批准的作業，可以做一次跨範圍檢視。這只是選項，帶著它的成本（需要各市場的系統與紀錄存取）；本案的範圍是台灣退款，這則訪談沒有提供任何跨市場的依賴關係，因此**不構成本案的工作要求，也不改變已議定的目標流程**。
