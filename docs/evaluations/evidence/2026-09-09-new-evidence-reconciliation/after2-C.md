# 新人報到流程：最小可行營運解

先講結論：這件事**多數的改善不需要 AI，也多半不需要新系統**。真正的瓶頸不是「IT / 門禁 / 教育訓練誰做得慢」，而是三條線各自從不同的起點被觸發、沒有單一負責人盯住「新人第一天可上工」這個結果。優先介入是**流程與權責重設計 + 一份共用的報到觸發事實**，把三條線改成報到日回推的並行前置作業。AI 在這個案子的判斷是 `AI not needed`（目前證據下不需要）。

以下用五段給你可以直接決定的內容。以下所有關於貴公司現況的敘述都是**參考假設（proposed）**，不是我查證過的事實——我沒有貴公司的流程紀錄、工單資料或報到排程資料。

---

## 1. 營運問題與目標成果

**使用者**：新進員工本人、其直屬主管、HR 報到承辦、IT 帳號開通、總務／門禁管理、部門訓練負責人。

**流程位置**：從「offer 接受、報到日確定」到「新人第一週結束、可獨立執行本職工作」。不含招募與試用期考核。

**營運成果（建議的衡量口徑）**：
- 主指標：報到日當天「可上工比率」——帳號可登入、門禁可進出、當週訓練已排定，三項全備的新人比例。
- 次指標：新人第一週實際等待工時；三條線各自的前置啟動日（相對報到日 D-n）。
- 這兩個指標目前是 `missing`，需要先量測，否則無法判斷改善幅度，也無法對主管交代。

**要做的決策**：這一輪要不要投入系統／工具，還是先用權責與時序重設計把等待壓掉。我的建議是後者先行。

**參考假設（待驗證，非事實）**：
- H1：三條線的觸發來源不同——IT 靠 HR 寄信或主管口頭、門禁靠報到當天才申請、訓練靠部門自行安排——所以啟動時間點分散。
- H2：至少一條線的前置作業其實可以在報到日前完成，但因為「人還沒到職」被當成不能先做。
- H3：新人第一週的等待，主要是**排隊等待**（工單躺在別人的待辦裡）而不是**作業耗時**（實際處理只要幾十分鐘）。
- H4：沒有任何一個角色被賦予「報到日全備」的責任，HR 只負責發起、IT/總務/部門各自只負責自己那段。

H3 是整個判斷的樞紐：如果等待來自排隊，答案是流程與時序；如果來自作業本身很慢或審批卡關，答案完全不同。

## 2. 現況診斷（要查的是這幾條路徑）

請照這四條路徑各走一次，最好拿最近 5–10 位新人的實際紀錄回推：

**正常路徑**：offer 接受 → HR 建檔 → 通知（怎麼通知？信件／表單／口頭？）→ IT 開帳號、總務製卡、部門排訓練 → 報到日。要記的是每個環節的「收到時間」與「完成時間」，兩者之差就是排隊時間。

**例外路徑**：報到日臨時提前、部門臨時異動、外包／約聘身分、需要特殊系統權限或跨廠區門禁。這些通常是等待時間的長尾來源。

**升級路徑**：卡住的時候誰去催？如果答案是「新人自己去問」或「主管自己去催」，那就是權責缺口的直接證據。

**重工路徑**：資料重複填寫（HR 表、IT 申請單、門禁申請單各填一次姓名／部門／到職日）、部門重複核對身分、訓練排完又因權限沒好而重排。

診斷時特別看這幾類浪費：
- **等待**：工單躺著沒人動的時間。
- **重複輸入與重複查核**：同一組人事事實被抄寫多次，每抄一次就是一個延遲點與錯誤點。
- **語意模糊**：「報到日」指的是到職生效日還是實際到班日？「部門」指的是成本中心還是實體組織？這種模糊會讓 IT 或門禁不敢先開通。
- **權責不明**：沒有人對「第一天全備」負責。
- **無效控管**：需要主管簽核才能開帳號——如果所有 offer 本來就已經過主管核准，這個簽核不降低任何實質風險，只增加等待。

## 3. 目標流程（不預設任何技術）

核心變更是**從「報到後依序申請」改成「報到日回推、三條線並行預備」**。

1. **單一觸發事實**：offer 接受、報到日與部門確定的那一刻，就是三條線的共同起點。HR 建檔完成 = 三方同時收到同一份人事事實（姓名、員編、部門、報到日、職務、地點）。這份事實只被輸入一次。
2. **並行前置**：三條線同時在 D-3 到 D-5（實際天數依你們的作業時間定）開始準備，各自把成果做到「已建立但未啟用」的狀態——帳號建好待啟用、門禁卡製好待開卡、訓練時段已排入行事曆。
3. **報到日只做啟用**：新人到場，三項同時生效。啟用是分鐘級動作，不是天級流程。
4. **明確的單一結果負責人**：指定一個角色（多數公司放在 HR 報到承辦或直屬主管）對「D 日全備」負責，並持有各線的完成狀態可視性。他不執行，但他有責任在 D-1 確認並催辦。
5. **例外走同一條路**：臨時提前、身分特殊的案子，用同一個觸發事實加上例外標記，不另開一條影子流程。

這個設計不需要任何新工具就能跑——D-5 一封含完整人事事實的通知 + D-1 的檢查點，就足以驗證假設。

## 4. 介入選擇與 AI 適配

依「穩定規則交給軟體，語言負擔才考慮 AI」逐項比較：

| 介入手段 | 這個案子適不適合 |
| --- | --- |
| **流程與權責變更** | **首選**。並行前置 + 單一結果負責人，成本近乎零，可在下一位新人身上試。 |
| **資訊與語意修復** | **次選，且與首選綁在一起**。統一「報到日」「部門」的定義，讓人事事實只輸入一次、三方共用。這是讓並行前置真的能跑起來的前提。 |
| **確定性軟體** | **視前兩項的結果再決定**。帳號開通、門禁權限、訓練排程都是穩定規則與狀態轉移，本質上適合自動化——但在流程沒理順之前導入，只會把混亂自動化。 |
| **介面支援** | 一份共用的報到狀態看板（哪些人、哪三項、什麼狀態）成本低、效果直接，可與首選同時做。 |
| **人工判斷** | 保留給特殊身分、特殊權限的個案。 |
| **AI 協助** | **AI not needed（目前證據下）**。這個流程的負擔是等待與權責，不是語言理解、綜整或有邊界的推理。沒有需要 AI 讀懂的非結構文件，也沒有需要 AI 判斷的模糊語意。若日後出現「新人問題大量重複、答案散在多份規章」的語言負擔，屆時 AI 問答才有討論的價值——那是另一個問題，不是這一個。 |
| **受管控的自動執行** | **不建議在此階段**。自動開通帳號與門禁是有持久性效果的寫入動作，需要先有授權、稽核、冪等、回復、可問責的擁有者這五項的直接證據。目前這些全部 `missing`。 |

**證據界線**：以上全部是基於一般營運型態的 `proposed` 判斷。任何關於「你們的瓶頸在 X」的說法在你量測之前都是假設，不是結論。我無法從這裡驗證貴公司的實際工單時間、審批規則或系統權限。

## 5. 下一個可問責的動作

**你（或 HR 主管）先做這一件事**：取最近 5–10 位新人，回填一張表——每人 × 三條線 × 三個時間點（觸發送出、開始處理、完成），加上報到日。一兩個小時的事，但它會直接判定 H3 成立與否，也給你改善前的基準線。

同一時間，這三件事需要**由有權限的角色決定**，不是我能決定的：

1. **誰對「D 日全備」負責**（決策，屬 HR 或營運主管的權責）。沒有這個角色，並行前置會退回各自為政。
2. **能不能在報到日前預先建立帳號與門禁卡（待啟用狀態）**（政策決定，屬資安／IT 治理與人資政策）。這是整個目標流程的關鍵前提；如果答案是不行，理由是什麼，第 3 節要重算。
3. **現行的簽核關卡各自在防什麼風險**（事實請求，需要 IT 與總務說明）。防得住的留，防不住的拿掉。

**回來之後**：把量測結果與這三題的答案給我，我會重算診斷與介入選擇——特別是如果 H3 不成立（等待來自作業本身或審批而非排隊），第 3 節的目標流程就得換一個方向。

**現在可以同時進行、不必等這些決策**：統一「報到日」「部門」的定義，以及把人事事實整理成一份三方共用的欄位清單。這兩件事在任何一種結論下都不會白做。
