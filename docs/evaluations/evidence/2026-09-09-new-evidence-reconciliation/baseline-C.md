# 新進員工報到流程改造：最小可行營運方案

結論先講：這是**流程與權責問題，不是工具問題**。核心病灶是「報到準備工作被綁在報到日之後才啟動，且沒有單一負責人」。第一波介入應該是把觸發點前移、把三條併行的準備線標準化成一份清單、指定一位報到協調人；AI 目前**不需要**（`AI not needed`）。

以下所有關於貴公司現況的敘述都是**參考假設**（reference hypothesis），不是既有證據。我沒有貴公司的實際流程紀錄、系統清單或工時數據，凡標示 `proposed` / `missing` 的項目都需要由實際流程負責人驗證。

---

## 1. 營運問題與目標成果

**使用者**：新進員工（承受等待）、用人主管（承受生產力損失）、HR 報到窗口、IT、總務／門禁、部門訓練負責人。

**流程位置**：從「offer 簽回／到職日確認」到「新人具備完整工作能力」之間的準備期與報到首週。注意問題的真正起點多半在報到日**之前**，不在報到當天。

**痛點（依你的描述）**：IT 帳號、門禁卡、部門教育訓練由三個互不協調的角色各自處理，新人第一週約有一半時間在等待。

**目標營運成果（建議設定，待負責人確認）**：
- 新人到職**第一天**即具備基本工作條件（帳號可登入、能進出工作區域、知道第一週該做什麼）
- 「等待中無法工作」的時間從約 50%（`proposed`，需實測）降到可接受水準
- 每個報到案件有**一位**可被追問進度的人

**需要的決策**：要不要指定報到協調角色、要不要把準備工作的觸發點從「報到日」前移到「offer 簽回日」。這兩個決策由 HR 主管與用人單位主管共同拍板。

**證據狀態**：
| 主張 | 狀態 |
| --- | --- |
| 三條準備線由不同人處理、彼此不協調 | `evidenced`（來自你的陳述） |
| 新人首週約一半時間在等 | `proposed`（未經量測的印象值） |
| 準備工作在報到日才啟動 | `missing`（最關鍵的待查事實） |
| 各線實際前置工時與卡點 | `missing` |
| 現有 HRIS／IT 工單系統可否承載清單 | `missing` |

## 2. 現況工作診斷

以典型企業報到流程推論（參考假設，請對照實況修正）：

**正常路徑**：HR 收到到職確認 → 各自通知 IT／總務／部門 → 三方各自排程 → 新人到職 → 逐項領取。問題在於「通知」與「完成」之間沒有共同的到期日，三方各按自己的隊列排序，而新人的報到日對他們而言只是眾多待辦中的一個日期。

**可辨識的浪費**：

- **等待（最大宗）**：帳號開通通常有跨系統依賴——需要員工編號才能建 AD 帳號，需要 AD 帳號才能配 email 與各業務系統權限。若員工編號在報到當天才產生，整條鏈條就從第一天才開始跑，串列的前置時間直接落在新人身上。這是「等待」而非「工作量」問題，加人力無效。
- **權責不清**：沒有人對「新人第一天能不能開工」這件事負責。HR 認為自己負責文書，IT 認為自己負責帳號，訓練負責人認為自己負責課程，**沒有人負責結果**。這是三條線各自都「準時完成自己那段」卻仍然整體失敗的典型結構。
- **重複查核**：新人資料（姓名、部門、職稱、主管、到職日）很可能被分別填寫在 HR 表單、IT 工單、門禁申請單三處。資料不一致就產生退件與重問。
- **語意含糊**：「教育訓練」在不同部門指涉不同東西（法遵必修？系統操作？跟著資深同仁做？），沒有共同定義就無法排程，也就無法在報到前預先排定。
- **例外路徑**：非標準職位（約聘、外籍、跨區域、需特殊系統權限）通常沒有預設路徑，每次都當作新問題重新協調，這類案件的等待時間會顯著更長。
- **升級路徑缺失**：新人第三天還沒有帳號時，該找誰？多數組織的答案是「新人自己去催」，這正是把協調成本轉嫁給組織裡最沒有能力承擔的人。

**未降低實質風險的控制**：若門禁卡或帳號申請需要多層簽核，值得檢視每一層簽核究竟阻止了什麼——用人主管已經核准這個人入職，後續逐項再核准一次，多半只是把已做過的決定重做一遍。

## 3. 目標工作流（不預設技術）

先做工作面的重整，這一層不需要任何新系統：

**消除**
- 取消已由聘僱核准涵蓋的重複簽核（標準職位的標準權限包）
- 取消新人自行追進度的隱性工作

**簡化**
- 資料只填一次：以一份權威的新人基本資料為準，三條線都取用同一份，不各自重填

**標準化**
- 依職位類型定義**入職套件**（onboarding package）：職位 A 對應哪些系統帳號、哪個門禁群組、哪些必修訓練。新人一旦歸類，準備內容即自動確定，不需逐案討論
- 把「教育訓練」拆成明確的三類：法遵必修、通用系統操作、部門專屬上手，各自有明確的形式、時長與負責人

**重新指派（關鍵）**
- 觸發點從「報到日」前移到「offer 簽回日」——這一項單獨就能吸收掉大部分串列等待
- 指定**報到協調人**（多數組織放在 HR，也可放在用人單位）：不執行三條線的工作，但對「第一天可開工」這個結果負責，並持有升級權
- 各線給出承諾到期日：一律為「報到日前一個工作日完成」，不是「報到後盡快」

**修復**
- 建立單一共用檢核清單，三線同視、狀態可見。載體可以先是共用試算表，不必是新系統

**目標狀態的第一天**：新人到職時帳號已建立待啟用、門禁卡已製作待領、首週行程已排定並寄出。第一天的內容是報到、認識人、開始受訓，不是等待。

## 4. 介入選擇與 AI 適配判斷

依「最簡可行」排序，建議依序進行：

**第一波：流程與權責變更（無需技術）**
觸發點前移、指定協調人、定義職位對應的入職套件、統一到期日、共用清單。這一波處理的是等待與權責，而等待與權責正是問題的主體。單靠這一波，多數組織就能把首週等待壓到很低。

**第二波：資訊與語意修復（無需技術）**
統一新人資料的權威來源；把「教育訓練」的定義釐清到可排程的粒度。

**第三波：決定性軟體（僅在前兩波之後）**
若第一波證實流程可行但人工追蹤成本仍高，再考慮把清單自動化：由 HRIS 事件觸發、依職位規則自動派工、逾期自動提醒與升級。這些全是**穩定規則**——條件、期限、權限對應、狀態轉換——屬於決定性軟體，不是 AI。多數企業的 HRIS 或工單系統已具備此能力，導入新工具前應先確認既有系統能做到什麼。

**AI 適配判斷：`AI not needed`**

這是完整的判斷，不是暫緩。理由：本案的實質負擔來自**等待、協調與權責歸屬**，不是語言解讀、綜整或有界推理。把 LLM 放進報到流程（例如新人問答機器人）不會縮短帳號開通時間，只會讓等待變得比較有人陪。

唯一可能的 AI 位置是報到後的「新人常見問題回答」，但那要等前三波做完、且有證據顯示新人的提問量確實構成人力負擔時才成立——目前這項證據 `missing`。若日後要評估，須與非 AI 的做法（一份寫得好的新人手冊、指定的 buddy）比較，證明它增加價值。

**證據限制**：以上介入排序建立在「準備工作啟動太晚」與「無單一負責人」這兩個參考假設上。若實測後發現真正瓶頸是別的（例如 IT 人力嚴重不足、或門禁卡製卡外包有固定七天工期），介入順序必須改變。第一波動作之前的量測不是額外工作，是決定做什麼的前提。

## 5. 下一個可問責的行動

**行動**：以最近 5 到 10 位新人為樣本，做一次流程實測。

**負責角色**：HR 流程負責人，與 IT、總務、一位用人主管配合。

**所需輸入**：每位新人的 offer 簽回日、到職日、以及三條線各自的「申請送出時間」與「實際可用時間」。

**可觀察的完成條件**：一張表能回答三個問題——各線的準備工作實際在報到前幾天啟動？各線從啟動到可用需要多久？哪一段是串列依賴、哪一段是隊列排序造成的？

**為什麼是這一步而不是直接改流程**：這份量測會直接決定「觸發點前移」能吃掉多少等待。如果數據顯示 IT 其實提前兩週就收到通知卻還是遲交，那問題是產能或優先序，前移觸發點無效，該做的是別的事。這是一天的工作量，換掉一整輪改錯方向的風險。

**接著的決策點**（量測完成後，由 HR 主管與用人單位主管共同決定）：是否設立報到協調角色、由誰擔任、以及是否採用「報到日前一個工作日完成」作為三線共同的承諾到期日。這兩項是政策與權責決定，屬於人的職責，不能由分析代決。
