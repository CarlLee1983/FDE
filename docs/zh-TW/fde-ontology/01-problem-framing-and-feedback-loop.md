## 圖表定義

此圖呈現以下交付迴路：

```text
業務主題 → 現場 FDE → 本體建模 → 應用交付 → 回饋與演進
```

業務部門、主管與第一線專家提供痛點、指標與流程。產出包括儀表板、代理、工作流程與可追溯的交付紀錄。管理儀表板彙整營收、效率與成本等成果。

## 所解決的問題

| 問題 | 直接後果 | 架構回應 |
| --- | --- | --- |
| 不同部門對相同術語有不同定義 | 報表、流程與 AI 輸出彼此衝突 | 本體層建立單一的語意事實來源 |
| 資料與知識分散於系統、文件與人員之間 | 應用程式缺少必要的業務脈絡 | 連接層持續擷取多種來源類型 |
| AI 無法安全執行業務動作 | 輸出無法落地，或承擔過高風險 | 治理後的動作、權限與稽核支援應用程式 |
| 專案成果僅留在個別團隊 | 探索與建模被重複進行，擴展受限 | 成果回寫並保留於本體中 |

## 價值鏈分析

### 從主題到可驗證的問題

「提升效率」無法直接交付。FDE 必須將其轉換為具體的工作流程、使用者角色、決策點、資料集與可衡量成果。

**建議：使用包含下列欄位的業務主題卡。**

| 欄位 | 用途 |
| --- | --- |
| 業務目標 | 要改善的營收、效率、成本、品質或風險 |
| 使用者與負責人 | 提出需求者、日常使用者、流程負責人與資料負責人 |
| 情境邊界 | 組織、產品、流程起訖與例外情況 |
| 決策或動作 | 使用者使用應用程式後必須做出的決定或採取的動作 |
| 衡量方式 | 基準值、目標、頻率與證據來源 |

### 從問題到本體

本體建模不是為資料庫資料表重新命名的工作。它回答在一個情境中存在哪些物件、關係與動作；誰可以使用它們；以及可在何種條件下使用。這是連結資料工程與業務規則的邊界。

### 從本體到應用程式

當儀表板、代理與工作流程共用相同的語意資產時，其量度、篩選條件與動作便能保持一致。例如，回答訂單問題的代理應使用已定義的 `Customer`、`Order` 與兩者之間的關係，而不是另行編造提示詞層級的定義。

### 從應用程式回到資產

交付過程中發現的例外、術語、資料缺口與新工作流程知識，應成為本體修訂的輸入。這條回饋路徑使應用程式的使用成為下一輪治理與建模的證據。

## 可追溯鏈

**建議：**每次交付都應可透過下列鏈結追溯：

```text
業務主題 → 情境與指標 → 資料來源 → 本體資產版本
→ 應用程式版本 → 執行／核准紀錄 → 成果指標 → 本體修訂
```

少了其中任一環節，成果就難以解釋、重現、稽核或重複利用。

## 成功條件與反模式

| 成功條件 | 反模式 |
| --- | --- |
| 問題具備使用者、流程節點與衡量標準 | 「打造一個 AI」本身就是全部需求 |
| 本體與應用程式使用相同的業務定義 | 儀表板、代理與工作流程各自定義術語 |
| 成果會更新營運工作與本體資產 | 概念驗證在沒有負責人或維護路徑下結束 |
| 在擴大前先驗證小型端到端情境 | 團隊一開始就嘗試建模整個企業 |

## 待釐清問題

1. 第一個業務主題、流程邊界與目標衡量指標是什麼？
2. 誰做出最終定義決策？誰負責日常維護這些定義？
3. 輸出是建議性、需人員核准，還是可自動執行？
