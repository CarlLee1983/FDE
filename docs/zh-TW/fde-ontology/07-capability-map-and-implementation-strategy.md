## 目的與範圍

本章將本體驅動的 FDE 模型轉換為實用的能力地圖。這是一項產品與技術設計提案，而非現有實作的證據：專案目前不含應用程式程式碼或技術限制。

建議的第一個目標刻意保持狹窄：讓一個業務情境能取得可信的企業脈絡、呈現其溯源，並支援下一項受控動作。系統應先能解釋並治理風險較低的工作，才逐步取得自動化更多工作的資格。

## 能力地圖

| 能力 | 使用者價值 | 核心職責 | 相依項目 |
| --- | --- | --- | --- |
| 業務情境定義 | 使交付始終對準可衡量的營運問題 | 記錄主題、參與者、流程節點、指標與驗收規則 | 責任歸屬明確的業務負責人 |
| 本體資產生命週期 | 讓所有應用程式共享業務意義 | 定義、版本化、檢視與淘汰物件、連結及動作 | 業務定義與治理 |
| 來源擷取與對齊 | 使可信資料與知識可用 | 連接來源、對應語意、檢查品質並記錄血緣 | 來源存取與來源負責人 |
| 受治理的脈絡擷取 | 讓使用者或代理基於相關且獲准的證據工作 | 將本體範圍解析為資料、知識與溯源 | 本體、擷取與授權 |
| 決策支援 | 將脈絡轉化為可理解的營運視圖 | 產出具證據的儀表板量測、答案或建議 | 受治理的脈絡擷取 |
| 受控動作執行 | 將已核准決策轉化為真實流程成果 | 驗證前置條件、視需要請求核准、回寫並稽核 | 已定義動作、目標系統介接器與授權 |
| 交付與營運治理 | 防止資產與應用程式過時 | 管理發布、檢視、可觀測性、事件回應與採用指標 | 前述全部能力 |

## 優先建置項目

### 能力 1：情境與指標登錄表

為每個已交付情境建立小型結構化紀錄。它建立業務主題與可觀測成果之間的連結。

| 最小欄位 | 重要原因 |
| --- | --- |
| 情境名稱與描述 | 賦予交付穩定的業務身分 |
| 流程節點與使用者角色 | 將範圍限制在真實工作 |
| 決策或動作 | 避免建置被動展示 |
| 指標基準與目標 | 建立價值檢驗 |
| 責任歸屬明確的業務負責人 | 解決定義與驗收問題 |
| 使用的本體資產與來源 | 建立可追溯鏈 |

此能力雖輕量，卻有高槓桿：它提供一份單一紀錄，往後每個儀表板、代理、工作流程與發布都可據以評判。

### 能力 2：本體資產登錄表

實作一個擁有物件、連結與動作生命週期的 **本體資產模組**。其介面應精簡：呼叫端請求已定義的資產版本，或提交受治理的變更；不應在分散的應用程式程式碼中操作原始定義。

**介面契約（概念性）：**

```text
getAsset(assetId, version) -> 受治理的資產定義
resolveScope(scenarioId) -> 允許的物件、連結、動作與定義
proposeChange(change) -> 可檢視的變更請求
releaseChange(changeId) -> 已發布的資產版本或驗證失敗
```

其實作可包含豐富的驗證、版本比較、所有權檢查與影響分析。這些複雜度應置於模組介面之後。如此應用程式可獲得槓桿，且定義變更時，維護者也能維持局部性。

### 能力 3：具溯源意識的脈絡擷取

實作一個 **脈絡解析模組**，接收使用者、情境，以及所請求的物件或問題。它只回傳已授權的企業脈絡，以及用於解釋該脈絡所需的證據。

```text
resolveContext(user, scenario, request) -> 脈絡套件

脈絡套件 =
  允許的物件與連結
  來源紀錄或文件參照
  本體資產版本
  資料新鮮度與品質狀態
  溯源參照
```

這是業務應用程式與來源系統之間的關鍵接縫。儀表板、代理或工作流程不應各自探索資料庫、檔案與權限。此模組隱藏來源連接、語意對應、授權與血緣，同時呈現一個可用的脈絡套件。

### 能力 4：受控動作編排

僅在唯讀擷取已獲信任後，才實作 **動作執行模組**。它會評估宣告的本體動作、檢查前置條件與權限、視需要請求核准、呼叫目標系統介接器，並發出稽核紀錄。

```text
prepareAction(actor, action, input) -> 提議動作或驗證失敗
approveAction(approver, actionRunId) -> 核准決定
executeAction(actionRunId) -> 附稽核參照的結果
```

此介面呈現受控生命週期，而非目標系統細節。其實作封裝重試、冪等性、回寫介接器、逾時處理與補償。這是一個深度模組：少量呼叫就能讓每個應用程式取得相同的安全行為。

## 建議交付順序

建置各自也持續有用的垂直切片。不要從打造通用代理平台或全公司知識圖譜開始。

| 切片 | 端到端成果 | 新增能力 | 驗收證據 |
| --- | --- | --- | --- |
| 1. 可信的唯讀查詢 | 具名使用者能從獲准證據回答一個情境問題 | 情境登錄表、最小本體資產、一個來源介接器、脈絡解析 | 答案識別來源、新鮮度、定義版本與存取決策 |
| 2. 共享營運視圖 | 相同情境以儀表板指標與證據軌跡呈現 | 建構在相同脈絡模組之上的指標計算與儀表板介接器 | 儀表板與查詢的定義及數值一致 |
| 3. 人工核准的建議 | 使用者收到建議的下一步動作，並可核准或拒絕 | 動作定義、建議記錄、核准步驟 | 每項建議呈現前置條件、證據、負責人與決策紀錄 |
| 4. 受控回寫 | 已核准動作安全地更新一個業務系統 | 動作執行、一個目標系統介接器、稽核與復原路徑 | 回寫已授權、具冪等性、可追溯且可復原 |
| 5. 相鄰情境重用 | 第二個情境重用大部分語意資產與控制 | 新情境紀錄與漸進式本體擴充 | 衡量重用；不建立既有概念的平行定義 |

## 模組接縫與所有權

提案中的模組刻意依變動關切組織。每個模組有一個介面，並可有多個內部介接器。唯有實際存在變異時，例如第二個來源系統或目標系統，才有理由加入介接器。

| 模組 | 外部介面負責事項 | 內部實作可隱藏項目 | 有需要時可能的介接器 |
| --- | --- | --- | --- |
| 情境登錄表模組 | 登錄並解析交付情境 | 驗證、所有權規則、指標中繼資料 | 初期無 |
| 本體資產模組 | 讀取已發布定義並治理變更 | 版本管理、影響分析、檢視工作流程 | 僅在儲存方式不同時使用儲存介接器 |
| 脈絡解析模組 | 回傳請求所允許且有來源的脈絡 | 來源路由、對應、資料品質檢查、血緣組裝 | ERP、CRM、文件與搜尋介接器 |
| 決策支援模組 | 從脈絡呈現量測、答案或建議 | 提示、計算、排序、呈現格式化 | 儀表板與模型介接器 |
| 動作執行模組 | 準備、核准並執行已宣告動作 | 前置條件、重試、冪等性、稽核與補償 | 工作流程、ERP、工單或訊息介接器 |
| 營運模組 | 回報健康度並處理檢視／發布事件 | 監控、告警路由、檢視排程、事件紀錄 | 僅在採用外部系統時使用可觀測性介接器 |

## 第一個切片的非目標

- 整個企業的通用本體。
- 高影響動作的自主執行。
- 在尚無使用案例前，擷取所有文件、試算表與系統。
- 為每個儀表板、代理或工作流程各自實作資料存取。
- 無版本提示詞或定義，且無法連結至業務成果。

## 架構決策規則

1. **一份定義，多方取用。** 指標或業務術語必須在本體資產模組中宣告一次，再供每個取用者重用。
2. **先讀後寫。** 在啟用回寫前，先證明擷取品質、溯源與存取控制。
3. **動作應被宣告，而非即興產生。** 代理可建議動作，但執行必須使用具名本體動作與明確條件。
4. **輸出附帶證據。** 答案、指標、建議與回寫都必須識別來源、定義版本與相關稽核軌跡。
5. **優先採用深度而非轉傳模組。** 模組應從呼叫端移除反覆出現的複雜度；避免只轉送資料的薄包裝。
6. **只為實際變異引入接縫。** 每種來源或目標類型先從一個介接器開始；當第二個真實介接器需要時再泛化。

## 驗證策略

| 層級 | 要驗證項目 | 範例證據 |
| --- | --- | --- |
| 本體資產 | 定義、負責人、來源、版本與影響均有效 | 所有權或來源遺漏時，提議資產變更會被拒絕 |
| 脈絡解析 | 存取、語意對應、新鮮度與溯源均正確 | 兩名使用者對相同請求取得不同的允許脈絡 |
| 決策支援 | 結果使用已解析脈絡，且不隱藏不確定性 | 儀表板與代理對指標及來源依據一致 |
| 動作執行 | 前置條件、核准、稽核、冪等性與復原皆運作 | 重複的已核准請求不會重複執行外部動作 |
| 情境成果 | 營運指標改善，或情境被淘汰 | 基準與發布後量測可重現 |

## 實作前所需決策

1. 哪個業務情境將成為第一個垂直切片？
2. 哪個來源系統能在有責任歸屬人的情況下提供所需唯讀資料？
3. 現有的哪些身分、權限與稽核機制必須整合？
4. 此專案適用哪些交付環境與技術限制？
5. 第一個受控回寫適合採取何種動作（若有）？

## 建議下一次工作會議

選定一個情境並填寫情境卡。接著定義其最小物件／連結／動作集合，以及一項產生證據的唯讀查詢。這會形成具體實作契約，而不會過早選定通用平台，也不會在首次有用目的前過度擴展本體。
